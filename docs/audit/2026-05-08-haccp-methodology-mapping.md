## 3. Связь с TasksFlow (адаптеры)

Из 35 шаблонов в каталоге есть **специализированные** адаптеры (33 в `src/lib/tasksflow-adapters/`):

| Журнал | Адаптер | Раздаёт race-задачи? | Pinned-узлы pipeline? |
|---|---|---|---|
| cleaning | `cleaning.ts` | ✓ (rooms-mode) | ✓ |
| hygiene | `hygiene.ts` | — | TODO |
| health_check | `health-check.ts` | — | TODO |
| climate_control | `climate.ts` | — | TODO |
| cold_equipment_control | `cold-equipment.ts` | — | TODO |
| pest_control | `pest-control.ts` | — | TODO |
| ... | ... | ... | ... |

**Generic-fallback:** есть `generic.ts`, который читает `JournalPipelineTemplate` из БД и рендерит pinned-узлы по `JournalTemplate.fields[]` (P1.4 закрыт `67e4b315`). Это означает, что любой журнал с заполненным template+pipeline можно прогнать через TF без отдельного адаптера.

**Что нужно проверить per-journal:**
1. Совпадают ли `JournalTemplate.fields[]` с колонками методички (см. §2 выше).
2. Адаптер пишет данные в правильные `JournalDocumentEntry.data[fieldKey]` (тот же ключ, что у поля в шаблоне).
3. Pipeline-tree (если есть кастомный) имеет pinned-узлы по всем required-полям из шаблона.
4. Выпадающие списки (select) имеют корректные опции (например, для `health_check` — «зд/отстранен/отп/в/б/л»).

## 4. Что предлагаю как porядок фиксов

Это **большая работа**, не одна `/loop`-итерация. Не могу её сделать в рамках одного коммита без чёткого приоритета.

**Я выделил 4 wave-а по убыванию срочности:**

### Wave 1 (P0 — закрыть критичные дыры в покрытии):
- ✗ §8.3 — добавить шаблон «Инструктаж по посторонним предметам» (отдельно от `staff_training`).
- ✗ §8.4 — добавить «Реестр договоров ХАССП» (с типами: дератизация, стирка, вывоз отходов, утилизация ламп).
- ✗ §8.10 — добавить «Документы безопасности готовой продукции» (паспорта, выходные сертификаты).
- ✗ Сан. визуальный контроль — отдельный шаблон по §2.3 методички.
- ✗ CAPA — отдельный шаблон по §2.9 (или расширить `accident_journal`).
- **Объём:** ~5 новых `JournalTemplate` + соответствующие fields + миграция БД (не трогаем существующие данные, только добавляем).

### Wave 2 (P1 — выровнять колонки существующих под методичку):
- `cold_equipment_control`: проверить 8:00/18:00 двукратный замер.
- `equipment_maintenance`: добавить колонку «вид ремонта», «инв. №» если их нет.
- `general_cleaning`: проверить planned vs actual date + концентрация средства.
- `pest_control`: 10 точек визуального контроля.
- `staff_training`: «оценка по тестированию», «ФИО инструктора».
- `health_check`: проверить кодировку зд/отстранен/отп/в/б/л.
- `incoming_raw_materials_control`: 7 колонок методички.
- **Объём:** edit `prisma/seed.ts`, изменения в `JournalTemplate.fields[]`, миграция данных существующих документов (если поле переименовалось).

### Wave 3 (P2 — выровнять адаптеры):
- Для каждого журнала из Wave 2 — проверить, что адаптер пишет в правильные ключи и pipeline покрывает все required-поля.
- Заполнить «pinned-узлы» через `/settings/journal-pipelines/<code>` для всех журналов которые сейчас идут через generic.
- **Объём:** аудит per-adapter, минимальные изменения по 1-2 поля каждый.

### Wave 4 (P3 — UI и интеграция):
- Связь между журналами: `incoming_raw_materials_control` → `traceability_test` (партия сырья → готовая продукция).
- Связь `health_check` → `hygiene` (если допуск к работе = «отстранен», то в гигиене сегодня этот сотрудник не учитывается).
- Связь `accident_journal` → CAPA (каждая авария порождает запись в CAPA).
- Связь `pest_control` → `accident_journal` (если найдены вредители — авария).
- **Объём:** cross-template hooks в `journal-auto-create.ts` или подобных.
