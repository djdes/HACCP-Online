# ФГИС «Меркурий» (ВетИС) — интеграция

Входящие ветеринарные сопроводительные документы (ВСД) приезжают в
WeSetup сами; менеджер в одном окне вводит физический контроль и одной
кнопкой получает строку журнала входного контроля и погашенный ВСД.

## Главное решение: автогашение по умолчанию ВЫКЛЮЧЕНО

`MercuryIntegration.autoProcessMode`, значение по умолчанию — `assisted`.

| Режим | Что делает |
|---|---|
| `off` | Только читаем. Журнал заполняется, гасит клиент сам в кабинете Меркурия. |
| `assisted` **(по умолчанию)** | Находим документ, считаем срок, напоминаем, заполняем строку журнала. **Гасит человек кнопкой.** |
| `auto_after_journal` | Гасит автоматически, но **только** после того, как человек заполнил строку входного контроля и поставил «принять», и только при полном совпадении объёма, и только для поставщиков из белого списка по ИНН. |

Чего мы не делаем **никогда**:

- не гасим по таймеру или при приближении дедлайна — просроченный ВСД
  это эскалация, а не повод подписать документ за клиента;
- не гасим по факту появления ВСД — без физической приёмки это запись
  о том, чего не было;
- не гасим пакетом без поимённого списка и подтверждения.

Обоснование простое: гашение — юридически значимое действие
уполномоченного лица хозяйствующего субъекта. Автоматизировать его без
физической приёмки значит обесценить журнал входного контроля (а он и
есть продукт) и взять на себя чужую ответственность.

## Учётные данные: что где живёт

| Что | Уровень | Где хранится |
|---|---|---|
| `MERCURY_API_KEY` — ключ ИС WeSetup | один на платформу | **env**, никогда в БД и никогда в UI |
| `MERCURY_SERVICE_LOGIN` / `MERCURY_SERVICE_PASSWORD` | платформа | env (нужны, если шлюз потребует Basic) |
| `MERCURY_ENV` (`test`\|`prod`) | платформа | env; базовый URL берётся из `ns.ts`, а не из БД |
| `issuerGuid` — ГУИД хозяйствующего субъекта | организация | `MercuryIntegration.issuerGuid`, открытым текстом |
| `initiatorLogin` — логин уполномоченного лица | организация | `MercuryIntegration.initiatorLogin` |
| `enterpriseGuid` площадок | организация | `MercuryEnterprise` |
| свой APIKey крупного клиента со своей ИС | редкий случай | `apiKeyEncrypted`, AES-256-GCM через `integration-crypto.ts` |

Отсюда следует, что **на странице подключения нет поля «API-ключ»** — в
отличие от TasksFlow. APIKey выдаётся один на информационную систему,
и клиенту он не нужен.

## Как получить доступ (делает владелец продукта)

1. `https://aplms.vetrf.ru/pub/` → «Получить доступ», флаг **тестовый
   контур**. Заявка подписывается ЭП, рассмотрение до 5 рабочих дней.
2. Приходят Login, Password, **APIKey** и **IssuerID**.
3. Каждый клиент подаёт заявку на **присоединение к существующей ИС**
   (нашей) и получает собственный `issuerId` под нашим APIKey.

## Разработка без доступов

Вся интеграция собрана так, чтобы её можно было писать и проверять до
получения ключей.

**Мок в памяти** (`mock-transport.ts` + `mock/store.ts`) честно
моделирует псевдоасинхронность: `submit` → `ACCEPTED`, первый
`receive` → `IN_PROCESS`, второй → `COMPLETED`. Он же умеет отвечать
«ВСД уже погашен» на повторное гашение — ветку, которая защищает от
двойного гашения, иначе не проверить.

**Мок-шлюз по HTTP** (`/api/dev/mercury-mock`, в проде отдаёт 404)
говорит настоящим SOAP, поэтому боевой `HttpSoapTransport` проходится
end-to-end:

```bash
MERCURY_MODE=live
MERCURY_API_KEY=dev
MERCURY_BASE_URL=http://localhost:3000/api/dev/mercury-mock
LOCAL_INTEGRATIONS_ALLOWED=1
```

Предохранитель: если в проде `MERCURY_MODE=mock`, интерфейс рисует
крупную плашку **«Демо-режим — данные не из Меркурия»** и на странице
настроек, и в списке ВСД. Принять учебные документы за настоящие —
худшее, что может сделать эта интеграция.

## Устройство

```
src/lib/mercury/
  types.ts             доменные типы, ноль XML
  ns.ts                namespace'ы, URL, имена операций  ← калибруется под боевой контур
  errors.ts            MercuryError + распознавание «уже погашен»
  deadline.ts          один рабочий день по календарю РФ + таймзоне организации
  access.ts            тариф и правила автогашения
  outbox-policy.ts     ЧИСТАЯ политика очереди — вся покрыта тестами
  vsd-to-acceptance-row.ts  ВСД → строка журнала приёмки
  xml/                 сборка и разбор
  transport.ts         интерфейс
  http-transport.ts    ЕДИНСТВЕННЫЙ файл, ходящий в сеть  ← калибруется
  mock-transport.ts    двойник в памяти
  client.ts            форма tasksflow-client.ts
  sync.ts              оркестрация: очередь + запись в БД
  process-incoming.ts  приёмка: строка журнала, партия, команда гашения
```

Ключевое отличие от очереди TasksFlow: там политика повторов зашита
внутрь обработчика крона и потому непроверяема, здесь она вынесена в
`outbox-policy.ts` и покрыта юнит-тестами целиком.

## Защита от двойного гашения

Заявки живут в Ветис **трое суток**; если крон лежал дольше, результат
потерян, а повторный `ProcessIncomingConsignment` на их стороне не
идемпотентен. Поэтому:

1. `@@unique([organizationId, uuid])` на `MercuryVetDocument`;
2. переход в `processing` только из `new | acknowledged | process_failed`;
3. протухшая **команда** не переотправляется вслепую: сначала
   `GetVetDocumentByUuid`, и если статус уже не `CONFIRMED` — считаем,
   что прошлая попытка дошла;
4. ошибка «ВСД уже погашен» трактуется как **успех**, а не как провал.

## Кроны — регистрируются на сервере вручную

В репозитории 33 крон-роута и внешнее расписание: новый роут сам себя не
пропишет (`docs/FEATURES_AND_AUTOMATION.md`).

```cron
* * * * *    curl -s "https://wesetup.ru/api/cron/mercury-outbox?secret=$CRON_SECRET" >/dev/null
*/10 * * * * curl -s "https://wesetup.ru/api/cron/mercury-poll?secret=$CRON_SECRET"  >/dev/null
```

Advisory-lock константы: `9523851` (очередь) и `9523852` (опрос).
`9523847` занят очередью TasksFlow — переиспользовать нельзя.

## Стадии

- **Стадия 0 — сделана.** Модели, весь `src/lib/mercury/*`, мок-шлюз,
  два крона, API-роуты, страница настроек и экран «Входящие ВСД»,
  маппинг в журнал приёмки, дедлайны, уведомления, тесты.
- **Стадия 1 — тестовый контур.** Нужны тестовые APIKey и ХС. Меняются
  только `http-transport.ts`, `ns.ts` и фикстуры: точные namespace'ы,
  `serviceId`, наличие Basic-авторизации, коды бизнес-ошибок и точный
  состав `deliveryFacts`. Закладывать 1–2 недели итераций.
- **Стадия 2 — прод.** После одобрения РСХН: `MERCURY_ENV=prod` и боевые
  секреты. Онбординг по одному клиенту, пилот минимум две недели.
  `auto_after_journal` не предлагаем никому, пока не наберётся ≥50
  успешных ручных гашений без расхождений.
