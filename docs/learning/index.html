Учебник для того, кто только начинает писать код и хочет перестать чувствовать себя пассажиром в собственном проекте. Здесь — карта твоей кодовой базы, физика веба, серверная кухня, кассы и принтеры, и честное сравнение языков.

Что ты получишь от этой книги

Эта книга — не справочник и не курс. Это карта. Карта проекта, в котором ты уже работаешь (Wesetup), и карта мира вокруг него — серверов, языков, протоколов, железа. Цель — чтобы ты перестал шарахаться от незнакомых слов и начал думать в категориях «откуда что берётся».

Чтение глав строго рекомендуется в порядке I → XII в первый раз. Потом — заходи в нужную главу как в справочник.

Как пользоваться

Открыл главу — прочитал — открыл соответствующий файл в проекте — потыкал руками. Без «потыкал руками» книга бесполезна. Чтение без практики оставляет иллюзию знания и нулевой навык.

Все примеры кода в этой книге — реальные, из твоего же репозитория. Когда видишь файл с путём вроде src/lib/auth-helpers.ts — он действительно существует, можно открыть.

Глава I

Карта проекта

Что лежит в каких папках, какие технологии работают вместе, и как не теряться в 800-строчной схеме Prisma.

Wesetup — это веб-приложение, написанное на фреймворке Next.js 16. Если разбирать на составляющие: фронтенд (React 19 + TypeScript), бэкенд (API routes того же Next.js, работающие на Node.js), база данных (PostgreSQL через ORM Prisma), и интеграции (Telegram-бот, TasksFlow API, email через Resend).

Всё это живёт в одном репозитории и собирается одной командой (npm run build) в одно приложение. Такая архитектура называется монолит — противоположность микросервисам. Для большинства задач это правильный выбор: одна кодовая база, одна точка деплоя, никаких распределённых транзакций.

Папки верхнего уровня

Wesetup.ru/
├── src/
│   ├── app/          # страницы и API routes (Next.js App Router)
│   ├── components/   # переиспользуемые React-компоненты
│   ├── lib/          # бизнес-логика, утилиты, доступ к БД
│   ├── content/      # блог (MDX-статьи)
│   └── types/        # типы TypeScript
├── prisma/
│   ├── schema.prisma # описание всех таблиц БД
│   └── seed.ts       # создание демо-данных
├── public/           # статика (картинки, иконки)
├── scripts/          # одноразовые скрипты (миграции, аудит)
├── docs/             # документация (включая эту книгу)
├── .github/workflows/# CI/CD (автодеплой на сервер)
└── package.json      # зависимости и npm-команды

Папка src/app/ — самое важное

В Next.js всё, что попадает в src/app/, становится маршрутом сайта. Файл page.tsx — это страница. Файл route.ts внутри api/ — это API-эндпоинт. Папки с круглыми скобками (например, (dashboard)) — это route groups: они группируют файлы для удобства, но в URL не попадают. 

src/app/
├── (auth)/login/page.tsx           → /login        # вход
├── (auth)/register/page.tsx        → /register     # регистрация
├── (dashboard)/dashboard/page.tsx  → /dashboard    # главная панель
├── (dashboard)/journals/[code]/page.tsx → /journals/hygiene
├── (root)/root/page.tsx            → /root         # только для суперадмина
├── mini/page.tsx                   → /mini         # Telegram Mini App
└── api/
    ├── journals/route.ts           → POST /api/journals
    ├── auth/[...nextauth]/route.ts → /api/auth/*
    └── mini/home/route.ts          → GET /api/mini/home
Запомни

Структура папок = структура URL. Это главная идея App Router. Хочешь добавить страницу /settings/printers — создаёшь файл src/app/(dashboard)/settings/printers/page.tsx. Хочешь API /api/cash/print — создаёшь src/app/api/cash/print/route.ts.

Папка src/lib/ — мозг проекта

Здесь — вся бизнес-логика, которая не должна знать о React и DOM'е. Чистые функции, обращения к БД, интеграции с внешними сервисами. Файлы page.tsx и route.ts в идеале только оркестрируют вызовы из lib/, а сами по себе тонкие.

Ключевые файлы, которые ты будешь открывать чаще всего:

  • db.ts — единственный экземпляр Prisma-клиента.
  • auth.ts и auth-helpers.ts — аутентификация, проверка ролей, мульти-тенантность.
  • journal-acl.ts — кто имеет право писать в какой журнал (с LRU-кэшем).
  • telegram.ts — отправка сообщений в Telegram-бот.
  • validators.ts — схемы валидации входящих данных (Zod).
  • tasksflow-adapters/* — интеграция с внешним TasksFlow.

Папка prisma/

Файл schema.prisma — это описание всей твоей базы данных на специальном языке (DSL). Из него генерируется TypeScript-клиент, через который ты пишешь запросы. Подробно — в главе VI.

В Wesetup сейчас около 800 строк в schema.prisma — это много, но каждый блок model X { ... } можно читать независимо. Не пытайся понять всё сразу: открывай только те модели, которые встречаются в задаче.

Что лежит в корне

  • package.json — список зависимостей и npm-скрипты (npm run dev, build, lint).
  • tsconfig.json — настройки TypeScript-компилятора.
  • tailwind.config.ts / postcss.config.js — настройки CSS-фреймворка Tailwind.
  • next.config.ts — настройки Next.js.
  • .env — секретные переменные (URL базы, токены). Никогда не коммитить!
  • CLAUDE.md — инструкции для AI-ассистента. Полезно прочитать — там описаны архитектурные принципы.
Практика

Прямо сейчас открой проект в редакторе. Не читая кода, пройдись по папкам src/app/ и src/lib/, и попробуй угадать по именам файлов «что делает этот модуль». Запиши 5 догадок. Потом откроем и проверим.

Глава II

Жизнь одного запроса

От клика в браузере до записи в Postgres и обратно. Реальный путь на примере «создать запись в журнале».

Главная вещь, которую нужно понять про веб: браузер и сервер — это две разные программы на разных компьютерах, которые общаются по сети через короткие сообщения. Каждое сообщение — это HTTP-запрос. Чтобы что-то сохранить, нужно послать на сервер запрос, дождаться ответа, и обновить интерфейс.

Веб — это переписка. Клиент пишет, сервер отвечает. Между ними — провода, протоколы и недоверие.

Возьмём конкретный сценарий: повар на кухне нажимает «Сохранить» на форме «новая запись в журнале температур». Что происходит за следующие 200 миллисекунд?

Что делает requireAuth

Первая проверка в любом API-хендлере — «а ты вообще залогинен?». Это делает функция getServerSession из NextAuth — она читает cookie, расшифровывает токен JWT внутри, и возвращает объект session с данными пользователя. Если cookie нет или токен невалиден — сервер отвечает 401 Unauthorized. 

// src/lib/auth-helpers.ts
export async function requireApiAuth(): Promise<ApiAuthResult> {
  const session = await getServerSession(authOptions);

  if (!session) {
    return {
      ok: false,
      response: NextResponse.json(
        { error: "Не авторизован" },
        { status: 401 }
      ),
    };
  }

  return { ok: true, session };
}

Что делает getActiveOrgId

У Wesetup мульти-тенантная архитектура: в одной базе данных живут сотни организаций (рестораны, кафе, пекарни), и они не должны видеть данные друг друга. Каждая таблица имеет колонку organizationId, и каждый SQL-запрос обязан фильтровать по ней.

Функция getActiveOrgId(session) возвращает ID текущей организации — обычно это та, к которой принадлежит пользователь. Но если суперадмин (ROOT) нажал «Войти как клиент X», возвращается ID этой клиентской организации. Любой запрос к БД должен использовать именно эту функцию.

Безопасность

Главный класс уязвимостей в мульти-тенантных приложениях — IDOR (Insecure Direct Object Reference). Это когда злоумышленник в URL подменяет ID и получает чужие данные. Защита — на каждом запросе явно проверять, что запрашиваемый ресурс принадлежит активной организации. Смотри как это сделано в journals/route.ts для areaId и equipmentId.

Что делает Zod

Данные, пришедшие от клиента, — это любая ерунда. Браузер мог быть скомпрометирован, клиент мог быть кастомным скриптом, форма могла прислать неполные данные. Поэтому первое, что делает сервер с body запроса, — проверяет его через схему. В Wesetup используется библиотека zod: 

// src/lib/validators.ts
export const journalEntrySchema = z.object({
  templateCode: z.string().min(1),
  areaId: z.string().optional(),
  equipmentId: z.string().optional(),
  data: z.record(z.string(), z.unknown()),
});

// в handler'е:
const parsed = journalEntrySchema.parse(body);
// если что-то не так — кидает ZodError, мы ловим и возвращаем 400

Что делает Prisma

Prisma — это ORM (Object-Relational Mapper): прослойка, которая превращает JavaScript-объекты в SQL-запросы и обратно. Вместо того чтобы писать INSERT INTO journal_entry ... руками, ты пишешь: 

const entry = await db.journalEntry.create({
  data: {
    templateId: template.id,
    organizationId: organizationId,
    filledById: session.user.id,
    data: data as Prisma.InputJsonValue,
    status: "submitted",
  },
});

Prisma сама генерирует SQL, посылает в Postgres, читает ответ, и отдаёт тебе типизированный объект entry. Если ты обратишься к полю, которого нет в схеме, — TypeScript подсветит ошибку до запуска.

Что происходит после успешного INSERT

В Wesetup сохранение записи — это не конец. Хендлер ещё проверяет: не было ли отклонения? (например, температура выше нормы). Если да — параллельно запускаются:

  • Отправка уведомления в Telegram (notifyOrganization).
  • Отправка email менеджерам.
  • Создание CAPA-тикета (расследование).
  • Отправка webhook'а внешним системам (Zapier-style).

Все эти операции — fire-and-forget, без await. Если Telegram упал, основной POST не ломается. Это паттерн «не блокируй пользователя сторонними сервисами».

Главный вывод главы: между кликом и ответом сервера происходит десяток шагов: сеть, прокси, проверка сессии, валидация, проверка ACL, проверка тенанта, запрос в БД, обработка результата, побочные эффекты, ответ. Когда что-то «не работает» — твоя задача определить на каком именно шаге сломалось, а не «переписать всё».
Глава III

Web-основы за вечер

HTML, CSS, JavaScript и почему именно эта тройка кормит половину IT-индустрии.

Любая веб-страница — это три слоя: HTML (структура), CSS (внешний вид), JavaScript (поведение). Без любого из трёх веб не работал бы так, как мы привыкли. Их легко спутать, но каждый отвечает за свою задачу.

HTML — структура и смысл

HTML — это разметка. Ты говоришь браузеру: «вот это заголовок, вот это абзац, вот это кнопка». Браузер превращает разметку в дерево объектов — DOM (Document Object Model) — с которым потом работают CSS и JS. 

<article>
  <h1>Журнал температур</h1>
  <p>Запись от 11 мая 2026</p>
  <button type="submit">Сохранить</button>
</article>

У каждого тега может быть атрибуты (type, href, class, id), и содержимое (текст или вложенные теги). Правильно подобранный тег важен — поисковые системы и screen reader'ы для слабовидящих понимают, что <article> — это статья, а <nav> — это навигация.

CSS — внешний вид

CSS говорит браузеру, как отрисовать каждый элемент. Цвета, размеры, отступы, шрифты, анимации. Селектор + свойства. 

.button-primary {
  background: #5566f6;
  color: white;
  padding: 12px 24px;
  border-radius: 8px;
  font-weight: 600;
  transition: background 150ms;
}

.button-primary:hover {
  background: #4a5bf0;
}

В Wesetup используется Tailwind CSS — это подход, при котором ты не пишешь свои классы, а используешь готовые из библиотеки: p-3 (padding), text-lg (font-size), rounded-2xl (border-radius), bg-[#5566f6] (background). HTML становится самодокументируемым, и не нужно поддерживать отдельный CSS-файл.

JavaScript — поведение

JavaScript — это язык программирования, который работает прямо в браузере. Он умеет: реагировать на клики, менять содержимое страницы, обращаться к серверу через fetch, хранить данные в localStorage. Без JS веб был бы статичным как книга. 

const button = document.querySelector(".save");

button.addEventListener("click", async () => {
  const response = await fetch("/api/journals", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ temperature: 4.2 }),
  });
  const data = await response.json();
  console.log("Создана запись:", data);
});

Что такое async и await

В JavaScript нет блокирующих операций. Запрос к серверу — это обещание (Promise), которое исполнится когда-то в будущем. Ключевое слово await говорит: «подожди этот промис, и только потом иди дальше». Функция, использующая await, должна быть помечена как async.

Почему так

Браузер не может «застыть» в ожидании ответа от сервера — иначе вся страница перестанет отзываться. Поэтому в JS все сетевые операции, чтение файлов, таймеры — асинхронные. Это самый частый источник багов у новичков: «почему console.log ничего не показал?». Скорее всего, ты забыл await.

Объекты, массивы, функции — три кита

Девяносто процентов JavaScript-кода — это трансформация объектов и массивов через функции. Запомни эти шесть методов и ты будешь свободно читать большую часть кода Wesetup: 

const entries = [
  { id: 1, temp: 4.2, ok: true },
  { id: 2, temp: 9.1, ok: false },
  { id: 3, temp: 3.8, ok: true },
];

// .map — преобразовать каждый элемент
const temps = entries.map(e => e.temp);
// → [4.2, 9.1, 3.8]

// .filter — оставить только подходящие
const good = entries.filter(e => e.ok);
// → [{id:1...}, {id:3...}]

// .find — найти первый подходящий
const bad = entries.find(e => !e.ok);
// → {id:2, temp:9.1, ok:false}

// .reduce — свернуть в одно значение
const avg = entries.reduce((sum, e) => sum + e.temp, 0) / entries.length;

// .some / .every — проверить условие
const anyBad = entries.some(e => !e.ok); // true
const allGood = entries.every(e => e.ok);  // false

Деструктуризация и спред

Две синтаксические конструкции, которые ты будешь видеть в каждом файле: 

// Деструктуризация — вынуть поля из объекта
const { id, temp } = entry;
// эквивалентно: const id = entry.id; const temp = entry.temp;

// Спред — раскрыть массив или объект
const updated = { ...entry, ok: false };
// новый объект со всеми полями entry, но ok=false
Не нужно учить JavaScript целиком за день. Достаточно понять синтаксис, базовые типы, асинхронность и пять методов массивов. Остальное — на практике, открывая код Wesetup.
Глава IV

TypeScript на практике

Зачем добавили типы к JavaScript, и почему теперь без них никто не делает серьёзных проектов.

TypeScript — это JavaScript плюс система типов. Любой валидный JS — это валидный TS, но в TS ты можешь сказать: «эта переменная — число», «эта функция принимает строку и возвращает массив объектов с такими полями».

Зачем это нужно? Чтобы редактор подсказывал тебе автодополнение, и чтобы компилятор ловил баги до запуска. Опечатался в имени поля? TS скажет «такого поля нет». Передал строку туда, где ждут число? Скажет. 

// JavaScript — никаких типов
function greet(user) {
  return "Привет, " + user.name;
}

// TypeScript — явные типы
function greet(user: { name: string }): string {
  return "Привет, " + user.name;
}

greet({ name: "Иван" });    // ОК
greet({ nme: "Иван" });     // ❌ TS: Property 'name' is missing
greet("Иван");               // ❌ TS: ожидался object

Базовые типы

const name: string = "Иван";
const age: number = 28;
const active: boolean = true;
const tags: string[] = ["a", "b"];
const nothing: null = null;
const empty: undefined = undefined;

// Объединение типов (union)
let status: "draft" | "submitted" | "approved" = "draft";

// Опциональные поля
type User = {
  id: string;
  email: string;
  phone?: string;  // ? означает «может быть undefined»
};

Interface vs type

Два способа описать форму объекта. Для новичка разница несущественна — выбирай type везде, пока не встретишь причину переключиться. 

interface User {
  id: string;
  email: string;
}

// то же самое через type:
type User = {
  id: string;
  email: string;
};

Generics — обобщённые типы

Когда функция или контейнер работает с разными типами одинаково. Самый узнаваемый пример — массив: 

type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: string };

function parseNumber(s: string): Result<number> {
  const n = Number(s);
  if (isNaN(n)) return { ok: false, error: "Не число" };
  return { ok: true, value: n };
}

Где в Wesetup тебе встретятся типы

  • Prisma-модели — автоматически генерируются из schema.prisma. После npx prisma generate ты получаешь типы User, JournalEntry, и т.д.
  • Zod-схемы — описывают форму входящих данных. z.infer<typeof journalEntrySchema> даёт TS-тип из схемы.
  • NextAuth session — расширенный в src/types/next-auth.d.ts.
  • Props компонентов — типы аргументов React-компонентов.
Совет

Если что-то «не компилируется» и ты не понимаешь почему — наведи мышью на красное подчёркивание в редакторе. TS пишет довольно осмысленные ошибки. Если запутался — запусти npx tsc --noEmit --skipLibCheck и прочитай весь список ошибок целиком.

Глава V

React и Next.js

Как из маленьких функций собираются большие интерфейсы, и почему один и тот же файл может выполниться на сервере и на клиенте.

React — это библиотека, в которой UI = функция от состояния. Ты пишешь компоненты — обычные JavaScript-функции, возвращающие разметку. React сравнивает новую разметку со старой и точечно обновляет браузер.

Простой компонент

function Button({ label, onClick }: { label: string; onClick: () => void }) {
  return (
    <button onClick={onClick} className="px-4 py-2 bg-indigo-600 rounded-xl">
      {label}
    </button>
  );
}

Функция называется Button, принимает два параметра (props): текст и обработчик клика. Возвращает разметку — это JSX, синтаксис, выглядящий как HTML внутри JS. После сборки <button> превратится в реальный DOM-элемент.

Состояние через useState

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Счёт: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}

Хук useState возвращает пару: текущее значение и функцию-сеттер. Когда ты вызываешь setCount(...), React заново вызывает функцию Counter с новым count, и обновляет ту часть DOM, где счёт поменялся.

Эффекты через useEffect

useEffect(() => {
  // этот код выполнится после рендера
  fetch("/api/mini/home")
    .then(r => r.json())
    .then(data => setHome(data));
}, []); // [] = выполнить один раз при монтировании

Server Components vs Client Components

Главная фишка Next.js App Router — компонент по умолчанию выполняется на сервере. Это значит: он может напрямую обращаться к БД, читать файлы, использовать секретные ключи. В браузер уходит уже готовая HTML-разметка.

Если компоненту нужна интерактивность (useState, обработчики кликов, useEffect), ты добавляешь в начало файла директиву "use client". Тогда компонент собирается в JS-бандл и оживает в браузере. 

// src/app/dashboard/page.tsx — Server Component (по умолчанию)
import { db } from "@/lib/db";

export default async function Page() {
  const users = await db.user.findMany(); // можно — мы на сервере
  return <div>{users.map(u => <p key={u.id}>{u.email}</p>)}</div>;
}
"use client";  // ← это Client Component
import { useState } from "react";

export function Counter() {
  const [n, setN] = useState(0);  // хуки доступны только в client
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
Правило

По умолчанию пиши Server Components. Переключайся на client только когда реально нужна интерактивность. Server-компоненты быстрее, меньше JS-бандл, лучше для SEO.

Route handlers (API)

Если в папке маршрута ты создаёшь файл route.ts вместо page.tsx, Next.js трактует его как API-эндпоинт. В нём экспортируются функции с именами HTTP-методов: GET, POST, PUT, DELETE. 

// src/app/api/printers/route.ts
import { NextResponse } from "next/server";

export async function GET() {
  return NextResponse.json({ printers: ["epson-tm-t88"] });
}

export async function POST(request: Request) {
  const body = await request.json();
  // ...логика...
  return NextResponse.json({ ok: true }, { status: 201 });
}

Динамические маршруты

Квадратные скобки в имени папки делают сегмент URL параметром. 

src/app/journals/[code]/page.tsx     → /journals/hygiene
                                       /journals/cleaning
                                       /journals/anything

src/app/api/users/[id]/route.ts      → /api/users/abc123
// в Next.js 16 params — Promise, всегда await
export default async function Page({
  params,
}: {
  params: Promise<{ code: string }>;
}) {
  const { code } = await params;
  return <h1>Журнал: {code}</h1>;
}

Что ещё умеет Next.js

  • SSR / SSG — рендеринг на сервере с кешированием.
  • Server Actions — функции, которые вызываются с клиента, но выполняются на сервере (без явного fetch).
  • Middleware — код, который выполняется до любого запроса (защита маршрутов).
  • Image optimization — компонент <Image> автоматически ресайзит и lazy-loadит картинки.
  • Hot reload — изменил файл, страница в браузере обновилась сама.
Глава VI

База данных и Prisma

Где живут данные, как Prisma превращает объекты в SQL, и почему ORM спасает от ручных запросов.

База данных — это программа, которая хранит данные на диске и позволяет искать в них по запросам. Wesetup использует PostgreSQL — открытую, надёжную, реляционную (то есть таблицы со связями между ними) СУБД.

Реляционная значит: у тебя есть таблицы с колонками и строками, как в Excel. Между таблицами есть связи через внешние ключи. Например, в таблице JournalEntry есть колонка organizationId, которая ссылается на строку в таблице Organization.

Что такое ORM

ORM (Object-Relational Mapper) — это прослойка, которая переводит объекты языка программирования в строки таблиц и обратно. Без ORM ты бы писал SQL руками: 

-- без ORM, чистый SQL
INSERT INTO journal_entry (id, template_id, organization_id, data, status)
VALUES ('cuid_xxx', 'tpl_temp', 'org_abc', '{"temperature": 4.2}', 'submitted');
// с Prisma — те же самые данные через TS
const entry = await db.journalEntry.create({
  data: {
    templateId: "tpl_temp",
    organizationId: "org_abc",
    data: { temperature: 4.2 },
    status: "submitted",
  },
});

Что ты получаешь взамен ручного SQL:

  • Типизация — TS знает, какие поля есть в таблице.
  • Защита от SQL-инъекций — данные пользователя автоматически экранируются.
  • Миграции — изменения схемы версионируются.
  • Читаемость — код понятнее без огромных строк SQL.

Файл schema.prisma

model Organization {
  id                       String     @id @default(cuid())
  name                     String
  type                     String
  subscriptionPlan         String     @default("trial")
  createdAt                DateTime   @default(now())
  updatedAt                DateTime   @updatedAt

  // Связь: одна организация — много пользователей
  users                    User[]
  journalEntries           JournalEntry[]
}

model User {
  id              String        @id @default(cuid())
  email           String        @unique
  role            String        @default("cook")

  organizationId  String
  organization    Organization  @relation(fields: [organizationId], references: [id])
}

Базовые операции

// CREATE — создать запись
const user = await db.user.create({
  data: { email: "ivan@cafe.ru", organizationId: "org_1" },
});

// READ — найти одну
const u = await db.user.findUnique({ where: { email: "ivan@cafe.ru" } });

// READ — найти много
const users = await db.user.findMany({
  where: { organizationId: "org_1", isActive: true },
  orderBy: { createdAt: "desc" },
  take: 20,
});

// UPDATE — изменить
await db.user.update({
  where: { id: "u_1" },
  data: { role: "manager" },
});

// DELETE — удалить
await db.user.delete({ where: { id: "u_1" } });

// Запрос со связями — подтянуть организацию вместе с user
const withOrg = await db.user.findUnique({
  where: { id: "u_1" },
  include: { organization: true },
});
// → { id: ..., email: ..., organization: { id: ..., name: ... } }

Миграции

Когда ты меняешь schema.prisma (добавил поле, новую таблицу), нужно «применить» эти изменения к реальной базе. Есть два пути:

  1. npx prisma db push — применить схему напрямую, без файла-миграции. Удобно для разработки и для этого проекта (в Wesetup используется этот подход).
  2. npx prisma migrate dev — создать SQL-файл с миграцией и применить его. Нужно когда требуется аккуратная история изменений (большие команды, production-grade проекты).
Безопасность

Никогда не доверяй данным от клиента в запросе к БД. Всегда фильтруй по organizationId активного юзера, проверяй ID на принадлежность к его организации, валидируй ввод через Zod. Самая частая уязвимость в реальных проектах — забытый where: { organizationId }.

Полезные команды

npx prisma db push      # применить схему к БД
npx prisma studio       # GUI для просмотра/правки данных в браузере
npx prisma format       # отформатировать schema.prisma

Серверная сторона

Linux, SSH, файловая система, процессы, nginx, PM2. Что находится по адресу wesetup.ru и как туда зайти.

Сервер — это компьютер, который работает 24/7, подключён к интернету и слушает входящие запросы. Wesetup живёт на одном сервере (виртуальная машина у хостинг- провайдера) с такими характеристиками: несколько CPU, несколько гигабайт RAM, диск, Ubuntu Linux.

Зайти на сервер по SSH

SSH (Secure Shell) — это протокол, по которому ты получаешь удалённый терминал на сервере. На Windows есть утилита plink (из набора PuTTY) или встроенный ssh в современных версиях.

Файловая система Linux

В Linux всё начинается с / (корень). Основные папки:

  • /home/имя/ — домашние папки пользователей.
  • /var/www/ — обычно здесь живут веб-приложения.
  • /etc/ — конфиги (nginx, ssh, cron).
  • /var/log/ — логи системы и приложений.
  • /usr/bin/ — установленные программы.
  • /tmp/ — временные файлы (очищаются при перезагрузке).

Wesetup развёрнут в /var/www/wesetupru/data/www/wesetup.ru/app.

PM2 — менеджер процессов

Node.js — это просто программа. Если ты запустишь npm start и закроешь терминал, программа умрёт. PM2 — это утилита, которая запускает Node-приложения в фоне, перезапускает их если они упали, и хранит логи. 

pm2 status                     # все процессы
pm2 status haccp-online        # один конкретный
pm2 logs haccp-online          # смотреть логи в реальном времени
pm2 restart haccp-online       # перезапустить
pm2 stop haccp-online          # остановить
pm2 start haccp-online         # запустить остановленный

pm2 monit                      # красивый мониторинг

nginx — reverse proxy

Node-приложение Wesetup слушает порт 3002 на 127.0.0.1 (только локально). Прямо снаружи его никто не видит. Между внешним интернетом и приложением стоит nginx — веб-сервер, который:

  • Слушает порт 80 (http) и 443 (https) на внешнем IP.
  • Получает запросы от пользователей.
  • Перенаправляет их на 127.0.0.1:3002.
  • Терминирует HTTPS (расшифровывает SSL).
  • Раздаёт статику (картинки) минуя Node.
# /etc/nginx/sites-enabled/wesetup
server {
    listen 443 ssl http2;
    server_name wesetup.ru;

    ssl_certificate     /etc/letsencrypt/live/wesetup.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/wesetup.ru/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3002;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

CI/CD — автодеплой

В .github/workflows/deploy.yml описан pipeline, который запускается при каждом git push origin master:

  1. GitHub забирает код.

Глава VIII

Docker и контейнеры

Зачем нужны контейнеры, чем они отличаются от виртуальных машин, и когда они тебе нужны (спойлер: не всегда).

Представь: ты написал приложение, которое работает на твоей машине. Деплоишь на сервер — не работает. Версия Node другая, какой-то библиотеки нет, права на папку не те. Эта проблема называется «у меня на машине работает». Docker — это способ её решить.

Что такое контейнер

Контейнер — это изолированный пакет с приложением и всем, что ему нужно: указанная версия интерпретатора, библиотеки, конфиги, файлы. Контейнер одинаково запускается на ноутбуке разработчика, на сервере, в облаке. Внутри — мини-операционная-система (обычно Alpine или Ubuntu Linux).

От виртуальных машин контейнеры отличаются тем, что используют ядро хост-системы. Это сильно быстрее и легче: контейнер запускается за секунды, занимает мегабайты.

Образ vs контейнер
Образ
nginx:1.25 — шаблон, рецепт. Скачивается из Docker Hub
↓ run
Контейнер
Запущенный экземпляр образа. Можно запустить много контейнеров из одного образа

Базовые команды

# Запустить контейнер
docker run -d --name web -p 8080:80 nginx

# -d  — detached, в фоне
# --name — имя контейнера
# -p 8080:80 — внешний порт 8080 проксировать на внутренний 80
# nginx — имя образа

# Посмотреть запущенные
docker ps

# Посмотреть все, включая остановленные
docker ps -a

# Логи контейнера
docker logs web -f

# Зайти внутрь контейнера
docker exec -it web bash

# Остановить и удалить
docker stop web
docker rm web

# Список образов
docker images

# Скачать образ
docker pull postgres:16

Dockerfile — описание сборки

Чтобы упаковать своё приложение, ты пишешь Dockerfile — инструкцию для Docker: 

FROM node:20-alpine                # берём базовый образ

WORKDIR /app                          # рабочая папка внутри контейнера

COPY package*.json ./                # копируем сначала зависимости
RUN npm ci                            # устанавливаем (кэшируется)

COPY . .                              # копируем остальной код
RUN npm run build                     # собираем

EXPOSE 3000                          # на каком порту слушает
CMD ["npm", "start"]                  # команда запуска
# Собрать образ
docker build -t my-app:latest .

# Запустить
docker run -d -p 3000:3000 my-app:latest

docker-compose — несколько контейнеров

Когда у проекта есть приложение + БД + Redis + nginx, запускать их по одному руками — мучение. Файл docker-compose.yml описывает всё разом: 

services:
  web:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - db
    environment:
      DATABASE_URL: "postgresql://postgres:secret@db:5432/app"

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
docker compose up -d        # поднять весь стек
docker compose logs -f      # логи всех сервисов
docker compose down         # остановить и удалить контейнеры

Когда Docker нужен

  • Если у проекта много сервисов (web + БД + кэш + очередь).
  • Если деплоишь в Kubernetes или другой оркестратор.
  • Если работаешь в команде и хочешь идентичную среду у всех.
  • Если нужно изолировать приложения друг от друга на одном сервере.

Когда Docker — лишнее

Wesetup сейчас работает без Docker — просто Node.js процесс под PM2. И это нормально для одного небольшого приложения с одной БД. Docker добавляет слой сложности, и если этот слой не нужен — лучше без него.

Прагматика

Если у тебя одна программа на одном сервере и она прекрасно работает — не нужно «контейнеризовать ради тренда». Docker — инструмент, а не цель.

Python и железо

Чековые принтеры, кассы, сканеры штрих-кодов, COM-порты. Почему здесь царствует Python.

В мире железа (POS-терминалы, чековые принтеры, фискальные регистраторы, сканеры, весы) почти всегда есть Python- библиотека для работы с устройством. Не PHP, не JS — а Python. Печать чека на ESC/POS-принтере

ESC/POS — стандарт команд для термопринтеров (Epson TM-T88, Star, большинство чековых). Библиотека python-escpos умеет работать с принтерами по USB, сети и serial-порту. 

from escpos.printer import Network, Usb, Serial

# По сети (если принтер с Ethernet-портом)
p = Network("192.168.1.50", port=9100)

# По USB (нужен idVendor/idProduct, lsusb покажет)
# p = Usb(0x04b8, 0x0e15)

# Печать
p.set(align="center", bold=True, double_height=True)
p.text("КАФЕ «БУЛКА»\n")
p.set(align="left", bold=False, double_height=False)
p.text("--------------------------------\n")
p.text("Капучино           180 ₽\n")
p.text("Круассан           120 ₽\n")
p.text("--------------------------------\n")
p.set(align="right", bold=True)
p.text("ИТОГО: 300 ₽\n")

p.qr("https://wesetup.ru/check/abc123", size=6)
p.cut()
p.close()

COM-порт и pyserial

Многие устройства — фискальные регистраторы, весы, старые сканеры — общаются через виртуальный COM-порт (RS-232 или USB-Serial). Библиотека pyserial: 

import serial

# Открыть порт
ser = serial.Serial(
    port="COM3",           # Linux: /dev/ttyUSB0
    baudrate=9600,
    bytesize=8,
    parity="N",
    stopbits=1,
    timeout=1,
)

# Послать команду
ser.write(b"\x02STATUS\x03")

# Читать ответ
response = ser.read(128)
print(response)

ser.close()

Фискальные регистраторы (РФ)

В России каждый чек должен идти через фискальный накопитель (ФН), сертифицированный ФНС. Для интеграции с моделями АТОЛ, Эвотор, Штрих — есть свои SDK:

  • АТОЛ Драйвер 10.x — официальный COM/Python API.
  • libfptr10 — кросс-платформенная C-библиотека (вызывается из Python через ctypes).
  • kkmserver — HTTP-обёртка для кассы (популярно у программистов 1С).
# Пример с libfptr10 (концептуально)
from libfptr10 import IFptr

fptr = IFptr()
fptr.setSettings({"Port": 3, "Model": 75})
fptr.open()

fptr.openReceipt(type="sell")
fptr.registration(name="Капучино", price=180, quantity=1)
fptr.payment(amount=180, type="cashless")
fptr.closeReceipt()

fptr.close()
Реальный мир

Документация у фискальных производителей в РФ обычно средняя. Будь готов читать форумы 1С, запрашивать примеры у поддержки и тестировать на реальном железе. Эмуляторы есть, но они не воспроизводят все баги живого ФН.

Чтение QR/штрих-кодов со сканера

Большинство USB-сканеров работают в режиме «keyboard wedge» — они эмулируют клавиатуру и просто «печатают» сосканированный код плюс Enter. То есть в браузере достаточно поля <input> с обработчиком onChange.

Если нужен низкоуровневый доступ — переключи сканер в режим serial и читай через pyserial.

Веб-сервер на Python — Flask

Если из Wesetup нужно вызывать локальное «железо» на компьютере официанта, на эту машину ставится маленький Python-сервер. Простейший — Flask: 

from flask import Flask, request, jsonify
from escpos.printer import Network

app = Flask(__name__)

@app.route("/print", methods=["POST"])
def print_receipt():
    data = request.json
    p = Network(data["printer_ip"])
    p.text(data["text"])
    p.cut()
    p.close()
    return jsonify({"ok": True})

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=5000)

Из Wesetup-клиента ты делаешь fetch("http://127.0.0.1:5000/print", { ... }) — и принтер печатает. Этот паттерн называется local companion app.

Глава X

Сравнение языков

Когда брать Python, когда Go, когда оставаться на JavaScript. Без религиозных войн.

Языков много, но большинство задач хорошо решается двумя- тремя из них. Главное — понять сильные стороны каждого, и тогда выбор становится очевидным.

Сравнительная таблица

Язык Типизация Скорость Где силён Где слаб
JavaScript динамика средняя веб-фронт, Node-бэк, скрипты числодробилки, железо
TypeScript статика = JS большие веб-проекты, full-stack тормозной билд, сложные типы
Python динамика низкая ML, скрипты, железо, наука, автоматизация веб-фронт, многопоточность
PHP динамика средняя сайты, CMS (WordPress, 1С-Битрикс) современная разработка, рынок труда
Go статика высокая сетевые сервисы, DevOps-тулы, CLI GUI, ML
Rust статика максимальная системное, embedded, WebAssembly порог входа, скорость разработки
C# / .NET статика высокая Windows-софт, Unity, корпоративные системы несколько перегружен фичами
Java статика высокая банки, Android, большие бэкенды многословность, JVM-багаж
Ruby динамика низкая быстрые MVP (Rails) падающая популярность

Как выбирать

Веб-приложение полного стека

→ TypeScript + Next.js. Один язык на фронте и на сервере, типы конец-в-конец, гигантская экосистема. Это твой текущий стек.

Скрипт «достать данные, что-то посчитать, выгрузить»

→ Python. Pandas, numpy, requests — всё под рукой. Скрипт пишется за час.

Работа с железом, кассами, принтерами, IoT

→ Python. Большая часть драйверов существует как Python-пакеты.

Высоконагруженный сетевой сервис, нужна максимальная производительность

→ Go или Rust. Go проще, Rust быстрее и безопаснее. Для большинства задач — Go.

Десктопное приложение под Windows

→ C# (.NET) или Electron (это веб-стек упакованный как desktop). Если только Windows и нужен native-look — C#. Если кросс-платформенно и команда веб-разработчиков — Electron.

Игра

→ C# + Unity для большинства игр. C++ + Unreal для AAA.

Android-приложение

→ Kotlin (native) или React Native / Flutter (кросс-платформа). В Wesetup мобильная часть сделана как Telegram Mini App — это просто веб-страница внутри Telegram, без native-приложения.

Почему именно Python, а не PHP?

Этот вопрос ты задал прямо. Честный ответ:

  • Экосистема для не-веб задач у Python гигантская: data science, ML, парсинг, автоматизация, железо, DevOps. У PHP — практически только веб.
  • Современная разработка идёт на Node/TS, Go, Rust, Python. PHP по-прежнему силён для классических сайтов (WordPress, Битрикс), но новые продукты на нём начинают редко.
  • Рынок труда. Python-разработчиков ищут повсюду (бэкенд, ML, аналитика). PHP-вакансий в РФ много, но в основном для поддержки legacy.
  • Чистота синтаксиса. Python субъективно приятнее читать после года практики.

Это не значит «PHP плохой». Современный PHP 8 — серьёзный язык с типами и хорошими фреймворками (Laravel, Symfony). Если ты работаешь в команде на PHP — продолжай, это нормально. Просто стартовать новый проект сегодня на PHP — нетипично.

Зачем TypeScript, если есть JavaScript

Когда проект становится больше 5000 строк, JS становится неуправляемым: ты не знаешь, какие поля у объекта, не знаешь, что возвращает функция, опечатки ломают всё в рантайме. TS убирает 80% этих проблем за счёт типов во время компиляции. Стоимость: чуть больше кода, чуть медленнее билд. Выгода: гораздо легче поддерживать.

Язык — это инструмент, а не идентичность. Выбор делается под задачу, не под социальную группу.
