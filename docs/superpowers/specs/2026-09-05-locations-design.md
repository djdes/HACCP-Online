# Точки (несколько локаций в одной организации) — дизайн

Дата: 2026-09-05. Статус: утверждён владельцем («1 вариант, всё реализуй,
продумай с учётом партнёров»).

## Задача

Организация с несколькими точками (сеть кафе, две столовые одного ИП)
ведёт журналы **отдельно по каждой точке**, а сотрудники, должности,
настройки и тариф — **общие**. В шапке — выпадающий список точек,
контент (журналы, документы, «сегодня») показывается для выбранной.
Число точек берётся из анкеты после регистрации («Точек»).

## Решение: точка = `Building`

Разведка показала, что «точка» в коде уже есть — это `Building`
(`/settings/buildings`, «корпуса (точки бизнеса)», адрес, порядок,
помещения внутри). `Area` — это цех/участок: к нему жёстко привязано
оборудование и он автоматически зеркалится из помещений, поэтому для
точек он не годится. Отдельная организация на точку (multi-org) не
подходит по постановке: там сотрудники не общие.

Итого:

| Понятие | Модель | Что меняется |
| --- | --- | --- |
| Точка | `Building` | становится единицей ведения журналов |
| Помещение | `Room` | без изменений, принадлежит точке |
| Цех/участок | `Area` | без изменений (оборудование) |
| Сотрудник | `User` | общий на организацию + `buildingIds` «работает на точках» |
| Документ журнала | `JournalDocument` | `buildingId` — к какой точке относится |
| Обязательство | `JournalObligation` | `buildingId` — по какой точке задача |

### Явное включение

`Organization.perLocationJournals Boolean @default(false)`. Пока флаг
выключен, всё работает как сегодня: здания — просто группы помещений,
переключателя нет, документы создаются без точки. Флаг включается:

- анкетой после регистрации, когда «Точек» ≥ 2 (создаются точки
  «Точка 1…N», первая получает адрес организации из ЕГРЮЛ);
- тумблером «Вести журналы отдельно по точкам» на `/settings/buildings`
  (виден при ≥ 2 зданиях).

Так существующие организации с несколькими корпусами одной площадки не
получают внезапного раздвоения документов после деплоя.

### Активная точка

- Хранится в cookie `wesetup.building` = `<orgId>:<buildingId>`
  (httpOnly, lax, год). Префикс организации делает значение
  бессмысленным после смены организации, импёрсонации ROOT или входа
  партнёра в другой кабинет — оно просто игнорируется.
- Сервер: `loadBuildingContext(session)` (кэш на запрос) читает здания
  организации, флаг и `buildingIds` пользователя и отдаёт
  `{ enabled, buildings, activeBuildingId, canSwitch }`. Правила:
  - флаг выключен или зданий < 2 → `activeBuildingId = null`
    (документы без фильтра, новые документы без точки);
  - у пользователя непустой `buildingIds` → выбирать можно только из них;
  - cookie указывает на недоступную/удалённую точку → первая доступная.
- `POST /api/me/active-building { buildingId }` проверяет, что точка
  принадлежит активной организации и доступна пользователю, ставит
  cookie, пишет `AuditLog building.switched`. Путь `/api/me/*` входит в
  allowlist записи для партнёров уровня «просмотр», поэтому партнёр в
  кабинете клиента переключает точки без дополнительных разрешений.
- `GET /api/me/active-building/go?building=…&next=/mini/…` — ставит
  cookie и редиректит (для перехода из обязательства Mini App в нужную
  точку). `next` только внутри `/mini`.

### Видимость документов

Предикат `buildingWhere(activeBuildingId)`:

- `null` → без фильтра;
- иначе `OR: [{ buildingId }, { buildingId: null }]` — документы без
  точки (созданные до включения флага) видны на каждой точке. Это же
  правило используют guard'ы ночного автосоздания, поэтому переход на
  точки происходит без дублей: пока жив общий документ периода, новые
  по точкам не создаются; со следующего периода документы рождаются на
  каждую точку.

Применяется во всех списках и «сегодня»-расчётах одного журнала:
`journals/[code]` (25 веток), `GET /api/journal-documents`, список
документов Mini App, меню документов в хлебных крошках, бейдж «есть
документ» на хабе, `today-status`, `today-compliance`
(`getTemplatesFilledToday`, `getTemplateTodaySummary`), catch-up,
close-day, journal-periods, auto-journals preview/apply,
`settings/auto-journals`, виджет «журналы сегодня», пул задач.

Не фильтруются (сводные по организации): отчёты, инспекторская ссылка,
экспорт/бэкап, поиск, партнёрская аналитика, ROOT.

### Создание документов

- Ручное создание (`POST /api/journal-documents`) — `buildingId` =
  активная точка.
- Ночные кроны (`auto-create-journals`, `journal-automation`), «Создать
  все документы», пересоздание из настроек ответственных, рассылка задач
  в TasksFlow — на **каждую точку** организации с включённым флагом
  (`buildingTargets(orgId)`: список id точек либо `[null]`).
- `ensureActiveDocument` / `ensureNextPeriodDocument` получают
  `buildingId`; guard'ы — по `buildingWhere`; конфиг «как в прошлом
  документе» и наследование ответственных — из документов той же точки
  (или общих); помещения журнала уборки — только помещения этой точки;
  ростер сотрудников (гигиена и т. п.) — сотрудники, работающие на этой
  точке (пустой `buildingIds` = везде).
- `closeExpiredDocuments`: преемник ищется в той же точке (или общий).
- `ensureCurrentDocumentsForBrokenChains`: при включённом флаге
  восстанавливает цепочку на каждую точку.
- Внешний API (`/api/external/entries`) точку не знает — документ общий.

### Шапка и Mini App

- Сайт: рядом с пилюлей организации пилюля точки «📍 Точка 1 ▾»
  (десктоп) и пункт в мобильном меню. Список точек грузится по активной
  организации (не по членству — иначе партнёр в кабинете клиента не
  увидел бы точек). Показывается только при `canSwitch`.
- Mini App: `/api/mini/home` отдаёт `location`; на главной чип с точкой
  (ссылка в профиль), в `/mini/me` блок «Точка» по образцу
  переключателя организации. Обязательства сотрудника показывают точку
  подписью; переход из обязательства сначала переключает точку.
- Шапка документа и PDF: под названием организации строка точки с
  адресом (`«Кафе» · Точка 2, ул. Ленина 5`).

### Сотрудники

- `User.buildingIds String[] @default([])`: пустой = работает на всех
  точках (обратная совместимость). Чипы «Точки» в диалогах добавления и
  редактирования сотрудника (при включённом флаге), пилюля точки в
  карточке сотрудника.
- Ограничение действует на: список точек в переключателе, ростер
  документов, обязательства (`getEligibleEmployees` ∩ точка).

### Обязательства и задачи

- `dedupeKey`: `daily:<дата>:<код>` без точки (как сейчас) и
  `daily:<дата>:<код>:<buildingId>` с точкой — уникальный ключ
  `[userId, dedupeKey]` не меняется. Сотрудник на двух точках получает
  по обязательству на каждую.
- `JournalObligation.buildingId` + подпись точки в Mini App и в
  Telegram-сводках.
- Пул задач (`journal-task-pool`): активный документ ищется по точке;
  org-scoped `scopeKey` получают сегмент точки.
- TasksFlow: рассылка идёт по каждому документу дня (каждой точке);
  название задачи, описание и ссылка получают « · Точка N»; сводка
  проверяющему уборки — тоже. Ключ `TasksFlowTaskLink` уже включает
  документ — схема не меняется.

### Партнёры и ROOT

- Партнёр в кабинете клиента видит переключатель и работает в выбранной
  точке (общий layout); партнёрская аналитика остаётся сводной.
- Партнёры уровня «просмотр» не могут создавать точки
  (`/api/settings/buildings` — запись, вне allowlist).
- ROOT при импёрсонации получает точки той организации, в которую вошёл.

### Ограничения v1 (осознанно)

- Уникальные ключи не меняются (деплой применяет `prisma db push` без
  флагов): «закрыть день без событий» (`JournalCloseEvent`) и превью
  журнала (`JournalPreview`) остаются на организацию.
- Поле-ориентированные журналы (`JournalEntry`) не делятся по точкам.
- Режима «Все точки» нет: всегда выбрана одна точка. Сводка по точкам —
  следующая задача.
- Удаление точки: документы остаются в организации и становятся общими
  (`onDelete: SetNull`).

## Схема

```prisma
model Organization { perLocationJournals Boolean @default(false) }
model Building { journalDocuments JournalDocument[]; obligations JournalObligation[] }
model JournalDocument { buildingId String?; building Building? @relation(onDelete: SetNull); @@index([organizationId, buildingId]) }
model JournalObligation { buildingId String?; building Building? @relation(onDelete: SetNull) }
model User { buildingIds String[] @default([]) }
```

Все изменения аддитивные: новые nullable-колонки, массив с дефолтом,
индексы, внешние ключи — `db push` применяет без предупреждений.
