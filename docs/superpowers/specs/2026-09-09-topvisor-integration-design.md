# Интеграция Topvisor: семантика и позиции под ROOT

Дата: 2026-09-09
Статус: спека заморожена, реализация не начата

## Зачем

Семантика и позиции wesetup.ru живут в Topvisor. Нужны две вещи, которых
там нет:

1. **Связка «фраза → посадочная страница → статья блога».** Topvisor знает,
   по какому URL сайт ранжируется, но не знает, что этот URL — статья в
   `/root/blog`. Wesetup знает и то, и другое.
2. **Возможность работать с семантикой через Claude.** Claude предлагает
   фразы, владелец утверждает галочками, утверждённые уходят в Topvisor.

Плюс удобство: не переключаться между админками и получать алерты о
падении позиций в тот же Telegram, куда уже идут обращения и оплаты.

## Границы

- **Только ROOT.** Один проект, никакой multi-tenancy, никаких прав.
  Организации Wesetup к Topvisor отношения не имеют.
- **Витрина, не хранилище.** История позиций живёт в Topvisor. Wesetup её
  не копирует.
- **Этап 1 — семантика и позиции.** Кластеризация, конкуренты и аудит
  сайта — отдельные спеки, если понадобятся.

## Проверенные факты об API

Всё ниже подтверждено боевыми запросами 2026-09-09, а не документацией.

### Аутентификация

Два заголовка, оба обязательны:

```
User-Id: 299034
Authorization: bearer <TOPVISOR_API_KEY>
```

Без `User-Id` API отвечает `{"errors":[{"code":53,"string":"Header 'User-Id' is missing"}]}`.

### Конверт ответа

**Topvisor отвечает HTTP 200 даже на ошибку.** `res.ok` не значит ничего.
Единственный признак ошибки — непустой `errors[]`:

```json
{"result": null, "errors": [{"code": 2004, "string": "…", "detail": {…}}]}
```

Это главная ловушка интеграции. Клиент обязан проверять `errors`, а не
статус.

### Формат `get/positions_2/history`

Запрос:

```json
{
  "project_id": 32866188,
  "regions_indexes": [1],
  "date1": "2026-09-01",
  "date2": "2026-09-09",
  "positions_fields": ["position", "relevant_url"],
  "show_exists_dates": 1
}
```

Ответ:

```json
{"result": {
  "headers": { "dates": ["2026-09-07"], "projects": [ … ] },
  "keywords": [{
    "name": "журналы хассп",
    "positionsData": {
      "2026-09-07:32866188:1": {
        "position": "14",
        "relevant_url": "https://wesetup.ru/zhurnal-haccp"
      }
    }
  }],
  "existsDates": ["2026-09-07"]
}}
```

Три особенности, которые определяют код:

- Ключ `positionsData` — составной: `<дата>:<project_id>:<region_index>`.
  Разбирать split по `:`, не полагаться на порядок вставки.
- `position` — **строка**, не число. Парсить в `Number`. Значение `"--"`
  означает «не найден в выдаче» — рендерить как «—», а не как `0` и не
  как `NaN`.
- `headers.dates` идут **по убыванию** (свежая первая).

Поля, которых **не существует** (проверено, ломают весь запрос):
`date_added`, `date_created`, `status` в `fields` у `projects_2`.

`tops` и `topsByDepth` приходят `null` даже с `show_tops: 1`. Сводку
ТОП-3/10/50 считаем на клиенте из самих позиций — отдельный запрос не
нужен.

### Формат цены и запуска съёма

Оба метода принимают одинаковый `filters` — стандартный фильтр Topvisor,
**не** `project_id` верхним уровнем:

```json
{
  "filters": [{"name": "id", "operator": "EQUALS", "values": [32866188]}],
  "regions_indexes": [1]
}
```

`get/positions_2/checker/price` возвращает:

```json
{"result": {"pricesByUsers": {"299034": {
  "projectsIds": [32866188], "price": 0.09,
  "priceOriginal": 0.09, "limits": 1
}}}}
```

`edit/positions_2/checker/go` возвращает `{"result":{"projectIds":[32866188]}}`
и ставит проверку в очередь. Результат появляется в `history` не мгновенно.

**Цена: 0,09 ₽ за одну пару «фраза × регион».** Баланс аккаунта на
2026-09-09 — 351,28 ₽.

Что это значит на практике:

| Фраз | Регионов | Цена прогона | Ежедневно, в месяц |
|---|---|---|---|
| 150 | 2 (Яндекс) | 27 ₽ | ~810 ₽ |
| 150 | 4 (Яндекс + Google) | 54 ₽ | ~1620 ₽ |

Текущего баланса на ежедневный съём не хватит. Дефолт — **2 региона
Яндекса, съём вручную**, не по расписанию Wesetup.

## Порядок работ

Владелец выбрал: **сначала семантика, экран потом**. Показывать матрицу с
одной строкой бессмысленно.

### Фаза 1 — клиент и наполнение семантики

1. `src/lib/topvisor.ts` — клиент.
2. Скрипт, которым Claude предлагает фразы и заливает утверждённые.
3. Наполнить проект `32866188` семантикой по блогу и лендингу.
4. Разово запустить съём, получить первые позиции.

### Фаза 2 — экран

5. API-роуты под `requireRoot()`.
6. `/root/seo` — матрица.
7. Крон алертов.

Фаза 2 начинается только когда в проекте есть фразы и хотя бы два съёма —
иначе нечего отлаживать.

## Архитектура

### `src/lib/topvisor.ts`

Одна низкоуровневая функция плюс тонкие обёртки:

```ts
class TopvisorError extends Error {
  constructor(public code: number, message: string) { super(message) }
}

async function tvRequest<T>(method: string, payload: unknown): Promise<T>
```

`tvRequest` обязан:

- слать оба заголовка;
- **проверять `errors[]`, а не `res.ok`** — иначе ошибки утекут как
  «успешный» ответ с `result: null`;
- бросать `TopvisorError` с кодом и текстом от Topvisor.

Обёртки: `listGroups`, `listKeywords`, `addKeywords`, `deleteKeywords`,
`getPositionsHistory`, `getCheckerPrice`, `runChecker`.

Конфигурация из env, проект — переменной, чтобы смена проекта не требовала
правки кода:

```
TOPVISOR_API_KEY=
TOPVISOR_USER_ID=299034
TOPVISOR_PROJECT_ID=32866188
```

Ключ читается только на сервере. В браузер не попадает никогда.

### Экран `/root/seo`

Матрица «фраза × дата», как в Topvisor.

- **Строки** — фразы. Под фразой — посадочный URL из `relevant_url`.
- **Колонки** — даты из `headers.dates`, свежая слева.
- **Ячейки** — позиция с подсветкой: ТОП-3, ТОП-10, ТОП-50, вне выдачи.
  `"--"` рендерится как «—».
- **Шапка** — селектор региона (4 варианта), сводка ТОП-3/10/50,
  кнопки «Добавить фразы» и «Снять позиции».

Связка с блогом: `relevant_url` нормализуется до pathname; если он вида
`/blog/<slug>` и такой `Article.slug` существует — показываем название
статьи ссылкой на `/root/blog`. Если фраза ранжируется, а статьи нет —
метка «нет посадочной». Это единственное, чего нет в самом Topvisor, и
ради этого экран и строится.

Кнопка «Снять позиции» обязана сначала дёрнуть `checker/price` и показать
`ConfirmDialog` с реальной суммой («Спишется 27 ₽ за 150 фраз × 2 региона»)
— тратить деньги молчаливым кликом нельзя. Удаление фраз — `ConfirmDialog`
с `typeToConfirm`, по правилу 6 из CLAUDE.md.

### Схема БД

Две маленькие таблицы. Копии Topvisor нет.

```prisma
/// Фразы, предложенные Claude, ждущие утверждения владельцем.
/// Не копия семантики Topvisor — только очередь на добавление.
model SeoKeywordDraft {
  id        String   @id @default(cuid())
  phrase    String   @unique
  reason    String?
  status    String   @default("pending") // pending | pushed | rejected
  createdAt DateTime @default(now())
  pushedAt  DateTime?
}

/// Анти-спам для алертов: о чём уже сообщили и на какой позиции.
model SeoAlertState {
  key          String   @id // "<phrase>:<region_index>"
  lastPosition Int
  notifiedAt   DateTime
}
```

### Крон алертов

`src/app/api/cron/seo-alerts/route.ts`, авторизация через
`checkCronSecret` из `src/lib/cron-auth.ts`.

Логика: один запрос `history` за период «сегодня минус 7 дней», сравнение
свежайшей даты с самой ранней в окне, отбор фраз с падением на 5+ позиций
или вылетом из ТОП-10. Отправка через готовый
`src/lib/platform-admin.ts`. `SeoAlertState` не даёт слать одно и то же
повторно — обновляется только когда позиция изменилась.

Крон **не запускает съём** и денег не тратит — только читает.

Расписание прописывается в crontab на сервере. Роут в репозитории
расписанием не является.

## Что осознанно не делаем

- **`WhatsNewModal` не трогаем.** `/root/*` видит только владелец
  платформы, модалка предназначена клиентам.
- **Не копируем историю позиций** в свою БД. Ради этого пришлось бы вести
  крон-снимки и разбираться с рассинхроном; ценности при одном
  пользователе нет.
- **Не делаем переключатель проектов** в UI. Проект задан переменной
  окружения.
- **Не трогаем `yesbeat.ru`.** Он в том же аккаунте, но к Wesetup
  отношения не имеет.
- **Не автоматизируем съём по расписанию Wesetup.** Это прямая трата
  денег; запуск остаётся ручным решением владельца.

## Критерии приёмки

- **AC1.** `tvRequest` бросает `TopvisorError` при непустом `errors[]`,
  даже когда HTTP-статус 200. Покрыто тестом с замоканным ответом.
- **AC2.** Парсер `positionsData` корректно разбирает составной ключ
  `<дата>:<project_id>:<region_index>` и превращает `"14"` в `14`,
  а `"--"` — в «не в выдаче». Покрыто тестом.
- **AC3.** `TOPVISOR_API_KEY` отсутствует в бандле клиента:
  `grep -r "$TOPVISOR_API_KEY" .next/static` ничего не находит.
- **AC4.** `/root/seo` недоступна не-ROOT пользователю (404).
- **AC5.** Кнопка «Снять позиции» показывает сумму из `checker/price`
  до подтверждения и не вызывает `checker/go` при отмене.
- **AC6.** Фраза с известной посадочной, совпадающей с `Article.slug`,
  рендерится ссылкой на статью; фраза без посадочной — меткой
  «нет посадочной».
- **AC7.** Крон алертов не отправляет повторное сообщение по той же паре
  «фраза + регион», если позиция не изменилась.
- **AC8.** `npx tsc --noEmit --skipLibCheck` и `npm run lint` проходят.
