## 2. План работ

### 2.1. `01020a41` — Баг: climate_control «не выполнен» при заполненных данных (ГЛАВНОЕ)

**Контекст.** Владелец (djtaang@gmail.com, орг. «ООО БФС») заполнил
`/journals/climate_control/documents/cmtd5diew00gmo0tsyd1hji23` «за сегодня»
(28.08, 19:12), но карточка «Бланк контроля температуры и влажности» на
дашборде красная, при этом «Гигиенический журнал» зелёный.

**Как считается статус.** Дашборд (`src/app/(dashboard)/dashboard/page.tsx:229`)
зовёт `getTemplatesFilledToday(orgId, now, templates, disabledCodes,
{ treatAperiodicAsFilled: false })` из `src/lib/today-compliance.ts`.
`climate_control` ∈ `DAILY_JOURNAL_CODES` (`src/lib/daily-journal-codes.ts:32`).
Для relaxed-журналов достаточно одной НЕ-seeded записи c `date = сегодня (UTC)`;
для strict (`fillMode === "per-employee"`, дефолт схемы —
`prisma/schema.prisma:1018`) — «сегодняшних ≥ последнего непустого дня».

**Три гипотезы причины (проверить в этом порядке):**

- **H1 — данные внесены не в ту строку.** На скриншоте владельца значения
  (1/1/2/3) стоят в строке **28-07-2026** (первая строка периода), а «сегодня»
  было 28-**08**. Число дня совпадает («28»), таблица открывается с начала
  периода, автоскролла к сегодняшней строке при обычном открытии нет
  (`FocusTodayScroller` срабатывает только с `?focus=today` —
  `src/components/journals/focus-today-scroller.tsx:15-18`,
  подключён в `climate-document-client.tsx:1515`). Тогда красный статус —
  формально «правильный», а баг — UX.
- **H2 — TasksFlow-strict правило стирает ручное заполнение.**
  `src/lib/today-compliance.ts:704-753`: если у организации включена
  TF-интеграция, для ЛЮБОГО daily-журнала с активным документом
  `filled.delete(templateId)`, когда TF-задач на сегодня нет или они не все
  закрыты — **любая ручная запись игнорируется**. У «БФС» на дашборде виден
  блок «Превью отправки задач TasksFlow», т.е. интеграция скорее всего
  включена. Гигиенический при этом зелёный из-за `JournalCloseEvent`-override
  (`:758-771` — автоматика `fa7f72c8` закрывает день) — что маскирует
  проблему и делает поведение непоследовательным для владельца.
- **H3 — таймзона.** `utcDayStart` (`:132-137`) считает «сегодня» в UTC.
  Коммит `d773c01b` починил зону только в **клиентах** документов; в
  `today-compliance.ts` про `Organization.timezone` ни слова. С 00:00 до
  03:00 МСК запись «за сегодня» сравнивается с UTC-вчера. На 19:12 МСК это
  не воспроизводится, но баг реальный и того же класса.

**Шаг 0 — диагностика на проде (30 минут, до любого кода):**

```bash
# SSH-доступ из CLAUDE.md (plink). В psql (креды из .env на сервере):

SELECT date, data FROM "JournalDocumentEntry"
 WHERE "documentId" = 'cmtd5diew00gmo0tsyd1hji23'
   AND data <> '{"_autoSeeded": true}'::jsonb ORDER BY date;
# 2) Включён ли TasksFlow у организации:
SELECT i.enabled FROM "TasksFlowIntegration" i
 JOIN "User" u ON u."organizationId" = i."organizationId"
 WHERE u.email = 'djtaang@gmail.com';
# 3) Почему hygiene зелёный (close events за сегодня):
SELECT "templateId", kind FROM "JournalCloseEvent"
 WHERE date = CURRENT_DATE AND "reopenedAt" IS NULL;
```

Если (1) вернёт только `2026-07-28` — подтверждена H1. Если (1) вернёт
`2026-08-28`, а (2) — `enabled=true` — подтверждена H2.

**Шаг 1 — фикс H2 (делать в любом случае, это несогласованность с П-10):**
в `src/lib/today-compliance.ts:720-753` и в зеркальной ветке
`getTemplateTodaySummary` (`:905-940`) изменить семантику:

- ветку «Нет TF-задач на сегодня → `filled.delete`» (`:734-737`) заменить на
  «нет TF-задач → **fallback на entry-эвристики**» (т.е. ничего не удалять);
- когда TF-задачи есть: `filled = entryFilled OR tf.allDoneToday` вместо
  безусловного `delete` при незакрытых задачах.

**Шаг 3 — фикс H3:** в `getTemplatesFilledToday`/`getTemplateTodaySummary`
считать `todayStart` в зоне организации: загрузить `Organization.timezone`

### 2.3. `480ead8b` — Дочинить подтверждение почты (ЧАСТИЧНО)

Сделано: баннер показывается только при `emailVerifiedAt IS NULL`, флоу
подтверждения живёт в одном месте (`/settings#email-verify`).

Осталось:
1. В `src/app/api/auth/register/confirm/route.ts` при создании владельца
   организации ставить `emailVerifiedAt: new Date()` — код из письма уже
   проверен строкой выше (`compareVerificationCode`, строка 123). Роут
   легаси, но живой — оставлять дыру нельзя.
2. Backfill для существующих аккаунтов: до перехода на instant-register
   (коммит `79a5bc5c`/`c10b6741`, задеплоен ~27.08) регистрация владельца
   была невозможна без кода из письма ⇒ у всех владельцев организаций,
   созданных до этой даты, почта фактически подтверждена. Однократный SQL на
   проде (точную дату cutover взять из `git log` деплоя):
   ```sql
   UPDATE "User" SET "emailVerifiedAt" = "createdAt"
    WHERE "emailVerifiedAt" IS NULL
      AND "createdAt" < '<дата деплоя instant-register>'
      AND role IN ('manager', 'owner');
   ```
   Сотрудников (`cook`/`waiter`/…) не трогаем — их почту никто не проверял.
3. (Опционально, обсудить) instant-register шлёт пароль на почту; первый
   успешный вход по этому паролю доказывает доступ к ящику — можно ставить
   `emailVerifiedAt` при первом логине, если пароль не менялся. Не делать
   без подтверждения владельца (открытый вопрос №4).

**Критерии приёмки:** у аккаунта djtaang в `/settings` баннер «Подтвердите
почту» исчез; новый аккаунт через старый роут получает `emailVerifiedAt`;
подтверждение из настроек работает как раньше.

**Риски:** backfill необратим — сначала `SELECT count(*)` с теми же
условиями и показать владельцу; не задеть аккаунты, созданные авто-
регистрацией после оплаты (они после cutover, под условие не попадают).
